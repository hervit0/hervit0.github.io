# Nova Vera: building an AI news pipeline that turns bias into a feature

> *First issued on 25/07/2026*

I built a piece of software that reads yesterday's news across the political spectrum, has a local LLM turn the day's most-covered stories into an Instagram carousel, and lets me review/edit every slide before anything gets posted. It's called **Nova Vera**, and it's the biggest personal project I've shipped: a real multi-service system (Java backend, React frontend, local LLM, image generation, external API integrations), not a weekend script.

This article covers why I built it, what it actually does, and the technical decisions and real bugs behind it — the kind of thing a game-jam side project rarely surfaces, but a "run every day and don't fall over" system does.

## The motivation

Two things pushed me toward this:

- **Media bias is exhausting to track by hand.** Reading the same story across a left-leaning, centrist and right-leaning outlet, every day, doesn't scale as a personal habit. I wanted software to do the tedious cross-referencing part — surface what multiple outlets are actually covering, label each source's leaning honestly, and never claim to be "unbiased" (a claim I don't trust from anyone) — while a human still makes the final editorial call.
- **I wanted a project that forces production-grade engineering, end to end.** Not a CRUD app, not a toy AI wrapper — something with a real external integration (Instagram's Graph API, with its actual quirks and undocumented gotchas), a real local-inference pipeline (LLM + image generation, no cloud spend), a real review UI, and enough moving parts that "test-first" and "log the actual bug, not just the fix" stop being nice ideas and become load-bearing.

It also nudged me to practice a stack I don't touch daily at work: Quarkus instead of Spring, a from-scratch canvas editor instead of a form, LangChain4j against a local Ollama model instead of a hosted API.

## What it does

The daily loop, as it stands today:

1. **Fetch** — pull every curated RSS source (a hand-rated spread across the bias spectrum: BBC, The Guardian, Sky News, The Telegraph, Daily Mail, Euronews, Deutsche Welle, and more), region-tagged (UK / Europe / Global).
2. **Cluster & rank** — group same-story articles across outlets by headline similarity, rank by cross-outlet coverage count + recency.
3. **Select** — a review page lists every candidate story for the day with a score (hover shows the coverage-vs-recency reasoning), top 8 preselected, reorderable, capped at 8 (leaving room for a branded cover + outro slide within Instagram's 10-slide carousel limit).
4. **Generate** — a local LLM (Ollama, no cloud key, no API spend) rewrites each selected story into a short title + ~300-character body, citing outlets, never copying source text verbatim (enforced by an actual validator, not just a prompt instruction).
5. **Review & edit** — every slide opens in a canvas editor: swap the photo (stock photo API, or generate an AI illustration instead, or upload your own), reword the text, drag/resize the layout, reorder or delete slides.
6. **Illustrate (optional)** — a slide's photo can instead be AI-generated: the LLM writes an editable image prompt from the slide's body text, a local ComfyUI instance renders it in a fixed pixel-art brand style — kept deliberately abstract/illustrative, never a photorealistic depiction of a real named person or event.
7. **Publish** — approve, and the exported PNGs get pushed to a secret GitHub Gist (Instagram's Content Publishing API needs a public HTTPS `image_url`, not an upload), then built into an Instagram carousel container and published via the Graph API. A manual export/download fallback exists if publish fails for any reason.
8. **Track** — a Performance page pulls live reach/likes/comments/saves/shares per published carousel and can summarize comment themes with the same local LLM.

It's a monorepo: `api/` (backend) and `webapp/` (frontend).

**Backend — Java, Quarkus, Gradle Kotlin DSL.** Panache/Hibernate ORM over PostgreSQL, Flyway-migrated (20+ migrations as the data model evolved — one carousel per day/region, one slide per story, shared across regions when a story qualifies for more than one). RSS ingestion via Rome. Clustering and ranking are pure, dependency-free logic (headline-token Jaccard similarity, coverage + recency scoring) — deliberately kept unit-testable without spinning up the whole app. Content generation goes through `quarkus-langchain4j` against a local Ollama instance, wrapped in a declarative `@RegisterAiService` interface so swapping the model — or pointing at a hosted one later — is a config change, not a rewrite. Illustration goes through a local ComfyUI instance via a plain REST client. Publishing pushes exported slide PNGs into a secret GitHub Gist using JGit (the Gist REST API is text-only — binary images need an actual git push), then drives Instagram's Graph API container→poll→publish flow.

**Frontend — React 19, TypeScript, Vite, MUI.** The slide editor is a `react-konva` canvas: photo/title/body as independently drag-and-resize-able nodes, a small custom `{photo, title, body}` layout schema (not raw Konva internals, so it isn't permanently coupled to one canvas library's serialization format), and `toDataURL()` for a direct PNG export that becomes the actual published image — no separate server-side rendering step. A background job queue (plain Postgres table, one worker thread — this runs one local Ollama/ComfyUI instance, no need for a real queue framework) handles bulk reword/illustrate so the UI doesn't block, and survives a page refresh mid-batch.

**No deployment.** Nova Vera runs entirely on my machine — Postgres via Docker Compose, Quarkus dev mode, Vite dev server, Ollama and ComfyUI on a second (Windows/GPU) machine on the same network. The only step that touches the internet at all is the publish step itself, and only because Instagram's API requires a public HTTPS URL to fetch the image from — everything else is local by design, including the review workflow. This is a deliberate v0 scope: proof-of-concept first, zero cloud spend, before ever considering an always-on host.

## Some real engineering, not just a demo

A few things I'm specifically proud of, because they came from real bugs and real production use against my own Instagram account rather than a happy-path demo:

- **The Graph API's undocumented gotchas.** Building the carousel container needs child containers joined as a comma-separated *string*, not a JSON array. A successful response sometimes comes back as `text/javascript` instead of `application/json` (a legacy JSONP leftover) — my REST client's default body-reader picked its parser off the actual `Content-Type` header and threw on a perfectly good response, so I added a response filter that normalizes it before Jackson ever sees it.
- **GitHub Gist's push authentication trap.** Pushing to a secret gist's git remote anonymously gets a `404`, not a `401` — Basic auth is never challenged, so a naive `CredentialsProvider` never gets to send the token at all. Fixed by embedding the token as URL userinfo so the very first request is already authenticated. (And a fine-grained GitHub token creates a gist fine over the REST API, but is silently rejected for the git push — only a classic token with the `gist` scope works there.)
- **A transaction-timeout bug, twice, at two layers.** Wrapping a whole multi-story LLM generation loop in one ambient database transaction meant a slow model response could outlive the transaction manager's timeout and get silently rolled back. I fixed it once at the service layer (short, separate transactions per story) — then found the exact same anti-pattern one layer up, in the REST resource, months later during an unrelated audit. Fixed properly this time with a dedicated, transaction-scoped view-assembly bean.
- **A genuine race condition, reproduced and fixed with a real concurrency test.** Two overlapping "fetch news" calls for the same day could both check "no draft yet" and both try to insert one — a classic check-then-insert race. I tried an in-place retry first, proved with a real two-thread test that Hibernate poisons the whole session once a flush throws, and landed on a Postgres advisory lock scoped to the transaction instead. Same pattern later reused for a second, independent race in article deduplication.
- **Test-first, genuinely.** The backend carries 180+ JUnit/Quarkus tests, the frontend 70+ Vitest tests plus Playwright end-to-end flows (fetch → select stories → reword → edit → approve → publish, fully network-mocked). Database-backed tests run against a real embedded Postgres binary rather than a Docker container, specifically so the whole suite is runnable without Docker at all. A progress log kept alongside the code (one entry per work session: what changed, why, what broke, what's still open) turned out to be as useful for spotting the same mistake happening twice as any linter.

## The automation endgame (designed for, not built yet)

Nova Vera is deliberately human-in-the-loop today — I review and approve every carousel before it posts. But the whole system is designed so that a future scheduler could drive it unattended: the "Approve" action is a thin, directly-callable trigger rather than something only a UI click can invoke, the pipeline steps (fetch, cluster, generate, publish) are independent REST endpoints rather than one monolithic flow, and secrets/config live in the database rather than developer-machine environment variables. Full automation needs an always-on host I don't have yet — that's future work, not a gap I'm pretending doesn't exist.

## Reflections and takeaways

This project taught me more about running software in the real world than any tutorial could: what actually breaks when an LLM call outlives a database transaction, why a "successful" HTTP response can still have the wrong `Content-Type`, how two well-intentioned bug fixes at different layers can silently reintroduce the same problem. Building something that has to run correctly *every single day* against a real external API, with a real (if small) audience on the other end, is a different kind of pressure than a portfolio piece that just needs to work once for a demo — and it's exactly the kind of pressure I wanted to practice under.
